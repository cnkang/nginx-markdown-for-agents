# 0.9.4 Release Checklist

**This checklist states requirements, not status.** The v0.9.4 candidate is
not a release. The evidence manifest must bind every record to one frozen
candidate SHA and one `release-packages.yml` run.

## Candidate preparation

- [ ] Keep v0.9.3 tags and Release assets intact.
- [ ] Keep the changelog and release notes marked Unreleased until publication.
- [ ] Synchronize active version metadata in Cargo, the chart, workflows, the
      doctor, and constrained documentation (Rule 55).
- [ ] Check `Cargo.lock` and `THIRD-PARTY-NOTICES` together (Rule 49).
- [ ] Verify the nginx.org tarball signatures and source checksums for 1.30.7
      and 1.31.9 against keys published by nginx.org.
- [ ] Confirm the 1.30.7 checksum remains unchanged.

## Compatibility evidence

- [ ] Build, load, and serve a Markdown request for stable 1.30.7 and mainline
      1.31.9 on glibc and musl, on amd64 and arm64: eight rows.
- [ ] Verify that each nginx.org target produces the required module tarball,
      DEB, and RPM assets under the release contract.
- [ ] On Ubuntu 24.04, verify exact revision `1.24.0-2ubuntu7.20` on amd64
      and arm64.
- [ ] On Ubuntu 26.04, verify exact revision `1.28.3-2ubuntu1.13` on amd64
      and arm64.
- [ ] For each Ubuntu row, verify source/binary matching, ABI provide, Brotli
      dependency, install, module load, Markdown request, and incompatible
      module rejection. Record all results in the CI evidence.
- [ ] Confirm each Ubuntu package revision is installable on both requested
      architectures. If an archive has advanced, stop and record the reason.
      Do not silently change the target.
- [ ] Use `promote_matrix.py` with the generated evidence, then regenerate
      the matrix projection and documentation. Do not hand-edit `verified`.
- [ ] Keep the benchmark-only runtime bound to the original performance
      baseline. Do not restore retired targets to the release support matrix.

## Release rehearsal and gates

- [ ] Run the required matrix, compatibility-evidence, docs, public-contract,
      regression, and security checks.
- [ ] Run Weekly Soak after the #335 fix. Retry Nightly LSan and confirm its
      sanitizer step ran. APT and other infrastructure failures are not tests.
- [ ] Dispatch `release-packages.yml` on the final candidate commit with
      `require_blocking=true`.
- [ ] Confirm the run's complete `head_sha` is the frozen candidate SHA. Every
      blocking row must have a record from this same run and SHA.
- [ ] Confirm RC, performance, short-soak, fuzz, and official Docker gates.
- [ ] Download the rehearsal artifacts and verify `release-manifest.json`,
      `SHA256SUMS`, package names, and checksums.
- [ ] Do not sign, tag, or create a GitHub Release during rehearsal.

## Maintainer handoff

- [ ] Record the PR URL, candidate SHA, workflow URL, blocking-row totals,
      evidence gaps, asset inventory, and remaining blockers.
- [ ] The maintainer must approve that exact SHA. The protected release must
      compare its `RELEASE_APPROVED_CANDIDATE_SHA` value to the approved SHA.
- [ ] After the protected signing workflow, verify the tag target and GPG
      signature, `SHA256SUMS.asc`, `release-manifest.json`, and downloaded
      assets. Do not change signing keys, environment approvals, or the
      candidate-SHA secret as part of this work.
