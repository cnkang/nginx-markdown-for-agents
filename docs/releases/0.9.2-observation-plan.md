# 0.9.2 observation plan

Observation is a separate, user-owned phase after local pre-LTS convergence.
Local tests can establish implementation behavior and host compatibility. They
cannot establish months of production stability. The current state is
`not-started` and `awaiting-soak-observation-external`.

## Phase boundary and scheduling

The local implementation phase ends when code, contract, support-matrix
evidence, and candidate checks are reviewable. The observation owner chooses
the environment, traffic window, start date, and gradual-rollout schedule. A
2–4 week gradual rollout is useful evidence but does not automatically qualify
the module for LTS. The plan records the candidate source SHA, working-tree
identity, build capabilities, NGINX version, host architecture, configuration
digest, traffic mix, and maintenance actions for every run.

The minimum long run is 72 hours in a supported core environment with multiple
workers. Lab load tests and production observation are separate records. A
short smoke result cannot qualify the long-run pass.

## Workload and fault coverage

The run mixes normal HTML and Markdown conversion with small, medium, and large
redacted pages. It exercises both full-buffer and streaming engines and all
five retained encodings: identity, gzip, zlib-wrapped deflate, raw deflate,
and Brotli. It repeats slow-read, client disconnect, upstream timeout,
truncation, budget-exhaustion, and reload scenarios. The traffic generator must
keep credentials and private URLs out of stored artifacts.

Use the native smoke and cache commands as preflight checks, then run the user-owned mixed-load harness:

```sh
bash tools/e2e/verify_chunked_streaming_native_e2e.sh --profile smoke --keep-artifacts
NGINX_BIN=/path/to/module-enabled-nginx \
  bash tools/e2e/verify_streaming_failure_cache_e2e.sh \
  --nginx-bin /path/to/module-enabled-nginx --keep-artifacts
# Run the approved 72-hour mixed-load driver in the supported environment.
# Record start/end, candidate identity, config digest, and all reports.
```

## Measurements and fixed thresholds

Set these thresholds before starting and do not loosen them after a failure:

| Signal | Threshold | Rationale |
|---|---:|---|
| Process crash or worker abort | 0 | Any crash is a release blocker. |
| Response-integrity mismatch | 0 | A client-visible mismatch is a correctness failure. |
| Credential or private URL exposure | 0 | Any exposure is a security failure. |
| Unbounded RSS growth after reclaim | 0 sustained growth across two load cycles | Detects leaks and unreclaimed old workers. |
| File-descriptor leak after reclaim | 0 sustained growth | Detects connection and temporary-file leaks. |
| P99 normal-request latency | Pre-run baseline + 25% | Keeps conversion load from masking normal traffic regressions. |
| Failed restart or rollback | 0 | Upgrade and recovery must be operable. |

The exact baseline value, worker count, traffic rate, and host limits belong in
the run record. A missing measurement is `not covered`. Never report it as “no
problem.”

## Reruns, fixes, and version separation

When a relevant security, correctness, crash, resource, or host-compatibility
fix lands, rerun the affected focused checks. Start a new observation segment
with a new candidate identity and keep the previous segment and its SHA. A
docs-only change does not mechanically reset the observation. Record the
rationale for that unrelated change. Start a new segment for a dependency change whenever it can affect
runtime behavior.

The capacity record [capacity-analysis.json](../../artifacts/release/0.9.2/capacity-analysis.json) remains pending until this plan supplies measured per-worker occupancy, memory, overlap, latency, and reclaim data. The six-status report records the distinction between local readiness and observation completion.
