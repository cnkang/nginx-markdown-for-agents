# 0.9.2 build, installation, upgrade, and rollback contract

This document defines the operator boundary for the 0.9.2 pre-LTS candidate.
The build is a source-delivery step. Installation, activation, and restart are
separate actions. The validation snapshot and host evidence appear in
[build-identity.json](../../artifacts/release/0.9.2/build-identity.json).

## Build identity

Use a clean checkout with the pinned `rust-toolchain.toml`, `Cargo.lock`, and cbindgen 0.29.4. Verify the NGINX source archive before unpacking it. The capability gate must report both `full_buffer` and `streaming`, plus `identity`, `gzip`, `zlib_deflate`, `raw_deflate`, and `brotli`:

```sh
make rust-lib RUST_RELEASE_FEATURES=streaming
make copy-headers check-headers
python3 tools/release/gates/verify_build_capabilities.py \
  --source-root . --write artifacts/release/0.9.2/capabilities.json
```

The build command writes to a temporary prefix or package staging directory. It does not copy a module into the active NGINX installation and does not reload or restart a service. The local arm64 run used Rust 1.98.1 (the repository's pinned build toolchain). The native x86_64 compatibility run on the validation host used the installed Rust 1.98.0 because that host has no rustup-managed 1.98.1 toolchain. The latter is compatibility evidence, not a byte-reproducibility claim. Rebuild the candidate with the pinned 1.98.1 toolchain before recording final release evidence.

## Install and enable

1. Record the current module path, NGINX version, active configuration path, metrics shared-memory name and size, and the current diagnostics response.
2. Build into a versioned staging directory. Run the capability gate and `nginx -t -p <staging-prefix> -c <candidate-config>` against the staged module and configuration.
3. Copy the module and any generated headers into a versioned install directory. Preserve the previous install directory and the original configuration as read-only rollback inputs.
4. Atomically replace the module symlink or package payload only after the staged `nginx -t` succeeds. Do not overwrite the active file in place.
5. Enable the module in the intended configuration, run `nginx -t` again, and
   record its output. A successful reload proves configuration syntax. It does
   not prove that workers loaded the new binary.
6. Restart the service through the normal supervisor. Verify the running worker
   identity with the read-only diagnostics endpoint and `nginx -V`. Record the
   module build identity, ABI version, feature digest, and worker start time.

The diagnostics endpoint is access-controlled and read-only. It does not accept an upgrade or rollback action and does not expose request credentials. The test `tests/compatibility/test_upgrade_rollback_contract.sh` checks the migration and failed-candidate behavior without touching a running service.

## Upgrade and schema lifecycle

The 0.9.2 ABI is version 3. A binary built with the old ABI must fail the
startup compatibility check. Metrics and diagnostics schemas carry explicit
version changes. Consumers must reject an old schema rather than treating the
new content as the old contract.

A configuration reload keeps existing workers until the normal graceful handoff
completes. A module replacement requires a verified restart. During a reload,
old and new workers can overlap, so capacity planning must reserve both
populations. External caches may contain responses from the old representation.
Purge or version those entries when deploying a representation-changing fix.
ETags and `Vary: Accept` remain representation-scoped. Failed streaming
responses are not eligible for complete-success caching. Operators may reuse
metrics shared memory only when its layout version and size match. The startup
check rejects an incompatible layout and never reinterprets it.

## Rollback and restore

1. Stop the rollout if the staged `nginx -t`, restart, diagnostics identity, or smoke request fails.
2. Keep the active module and configuration untouched until the replacement has passed syntax validation and a verified restart.
3. Restore the previous module payload and configuration atomically from the saved versioned paths.
4. Run `nginx -t`, restart, and verify the previous build identity and response behavior. A reload alone is insufficient evidence.
5. Preserve the failed candidate logs, the failed diagnostics request, and the rollback result for the candidate evidence record.

The rollback contract is intentionally conservative. An invalid candidate must
not mutate the active configuration. The real-NGINX test rejects an invalid
candidate and compares the active file with its pre-validation copy. The
old-release migration check covers a configuration containing
`markdown_dynamic_config`. It must fail with a migration message rather than
silently selecting a legacy behavior.

## Not covered by this local validation

This workspace did not install into a production prefix, exercise an Ubuntu
default-repository package, or perform a live module replacement. Those
operations remain operator-owned. Operators must record them separately from
the source-build evidence.
