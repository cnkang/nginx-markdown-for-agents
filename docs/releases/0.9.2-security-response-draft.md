# 0.9.2 security response policy (draft)

**Status: draft.** This policy is not yet effective. The decision owner must
approve and publish it before it governs the observation phase.

## Acknowledgment and classification

The maintainer on duty acknowledges a report within 48 hours. The maintainer
records the affected version, host/build identity, exposure, reproducibility,
and whether the report could expose credentials or client data. Within 7 days, the
maintainer classifies severity, defines a mitigation, and identifies the
focused verification required for the affected path.

The fix date is risk-determined. A confirmed credential exposure, remote code execution, data disclosure, crash loop, or response-integrity failure receives an emergency path. Lower-risk findings follow the next compatible maintenance window. The maintainer records the reason for the selected date.

## Fix and release handling

A security dependency update is necessary when it closes an applicable
vulnerability or restores a supported host/toolchain. The observation-freeze
policy defers non-essential upgrades. The response record includes the source
SHA, dependency lock diff, capability report, affected schemas, cache/ETag
impact, and rollback input.

This round records the drill as a procedure. Analyze the finding, make the
smallest fix, build with the pinned inputs, and run focused and GCC validation.
Stage an atomic upgrade and verify the loaded identity after restart. Restore
the previous module and verify rollback. Production execution remains
user-authorized and is not implied by this draft.

## Communication and closure

The maintainer keeps the report private until a mitigation and disclosure
decision exist. Closure requires the fixed version or an explicit accepted-risk
decision, evidence of the affected verification, and a link to the rollback
record. Record a pending observation or unavailable environment as such. Do
not convert it into a pass.
