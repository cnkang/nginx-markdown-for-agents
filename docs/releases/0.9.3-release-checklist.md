# 0.9.3 Release Checklist

**This checklist states requirements, not status.** It records what the 0.9.3
release must satisfy. It does not record the state of a candidate.

The evidence manifest defines whether one candidate satisfies these
requirements. The manifest binds every record to the frozen `candidate_sha`,
so evidence for one commit is never read as evidence for another commit.

## Pre-Release

- [ ] Merge every 0.9.3 change to the release branch and to `main`.
- [ ] `CHANGELOG.md` has a `[0.9.3]` section with the publication date.
- [ ] `docs/releases/0.9.3-release-notes.md` carries the final status and the
      publication date.
- [ ] `docs/guides/UPGRADE-TO-0.9.3.md` and
      `docs/guides/VERSION_ROLLBACK-0.9.3.md` are current.
- [ ] Version references agree in `Cargo.toml`, the chart, the workflows, the
      doctor, and the documentation (Rule 55).
- [ ] `THIRD-PARTY-NOTICES` matches `Cargo.lock` (Rule 49).

## Compatibility

- [ ] `packaging/checksums.sha256` contains a verified SHA-256 for every NGINX
      source tarball that the release matrix builds.
- [ ] Each current nginx.org stable and mainline row is `supported`,
      `verified`, and release blocking, for glibc and musl on both
      architectures.
- [ ] Each Ubuntu-native row records its exact package revision, its ABI
      provide, and one evidence record per architecture.
- [ ] No `verified` row lacks an evidence record.
- [ ] No `release_blocking` row lacks a workflow job that the publish job
      depends on.
- [ ] A superseded patch is `best-effort` and not release blocking.

## Evidence

- [ ] Each evidence record names the source revision, the module checksum, the
      configure argument digest, the test list, the run URL, and the commit.
- [ ] Each record has zero failed tests and zero skipped tests.
- [ ] Each Ubuntu record includes the incompatible-module rejection test.
- [ ] Produce every record from the frozen candidate SHA.

## Gates

- [ ] `make test-all`
- [ ] `make docs-check`
- [ ] `make release-matrix-check`
- [ ] `make compatibility-evidence-check`
- [ ] `make release-gates-check-093`
- [ ] `make security-static`
- [ ] The CodeQL and SonarCloud results for the candidate contain no open
      blocking finding.

## Release Day

1. Approve one publication date and one release status.
2. Use that date in the `[0.9.3]` changelog entry, in the release notes, and in
   the project status documents.
3. Synchronize the pending-state surfaces. The authoritative list is
   `PENDING_STATE_SURFACES` in `tools/docs/check_docs.py`.
4. Freeze the candidate SHA. Generate the evidence bundle for that SHA only.
5. Publish the tag from the frozen SHA through the protected
   `release-signing` environment.
6. Confirm these assets after publication:
   - The nginx.org DEB and RPM packages for each supported version.
   - The glibc and musl module tarballs.
   - The Ubuntu-native DEB packages for 24.04 and 26.04.
   - `SHA256SUMS`, `SHA256SUMS.asc`, and `release-manifest.json`.
7. Run `make docs-check` again against the published state.
8. Record the published source archive digest for audit.

## Rollback

- [ ] The previous release assets stay published.
- [ ] The previous module package file is available for a same-ABI rollback.
- [ ] The release notes name the rollback limits.
