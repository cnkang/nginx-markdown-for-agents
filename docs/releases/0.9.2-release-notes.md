# Release Notes: 0.9.2 Development Candidate

**Release date:** Pending release evidence and publication

**Compatibility target:** Breaking. 0.9.2 is the final breaking release
before 1.0. The release reduces the configuration surface from 63 directives to 25. It deletes all previously removed directives and removes profiles, OTel, per-path
metrics, and shadow mode. See
[0.9.2-breaking-changes.md](../guides/0.9.2-breaking-changes.md) for the
complete breaking-change reference and
[MIGRATION-0.9.2.md](../guides/MIGRATION-0.9.2.md) for before/after examples.
0.9.1 configurations using any removed directive fail `nginx -t` until
migrated.

**Status**: Unreleased. This document describes the branch candidate only.
It does not assert that a tag, GitHub Release, package, or checksum exists.

---

## Summary

nginx-markdown-for-agents 0.9.2 is a breaking maintenance and hardening
release: it freezes the public configuration surface at 25 directives
(removing profiles, OTel, per-path metrics, shadow mode, and the remaining
legacy directives), fixes diagnostics and reason-code mapping gaps, removes
an unsafe worker-local dynconf restore path, and establishes a public
surface contract drift gate for release integrity.

---

## Fixed

### Diagnostics `bypass_no_transform` Reason Coverage

The `bypass_no_transform` reason code (numeric 25) was previously missing
from the decision chain's reason coverage. Operators relying on the
diagnostics JSON to observe the reason string in `recent_decisions[].reason`
could not see this entry. The reason is now emitted by the decision chain and
appears in `recent_decisions` entries.

### C Reason Code Constants Missing Decompression Series (4–11)

The C implementation defining reason code constants did not include the
decompression error series (codes 4–11: `decompression_error`,
`decompression_budget_exceeded`, `decompression_format_error`,
`decompression_truncated_input`, `decompression_io_error`, and the
related timeout/budget/replay codes). The Rust converter emitted these
codes, but the C module could not reference them by symbolic name.
All 27 reason code constants are now synchronized between Rust and C,
including `encoding_header_invalid`.

### Streaming decision-state cleanup

The project retired the standalone C/Rust streaming decision-state model and
its self-proving tests. The production path retains only the runtime phase and
terminal latches required for backpressure, request lifetime, and exactly-once
terminal delivery. Streaming diagnostics now use the shared lowercase reason
registry and structured `event=` field, so the implementation no longer carries
a second obsolete `PRE_COMMIT` decision model.

### Prometheus `streaming_events_total` Fallback Reason Label

The `nginx_markdown_streaming_events_total{transition="fallback"}` metric
now reports `reason="precommit_html_error"`, which matches the logged
reason at the fallback decision. It previously reported the incorrect
`reason="bypass_no_transform"`. Update dashboards keyed on the previous
label value.

## Added and Removed

### Dynconf JSON v1 migration

0.9.2 freezes dynamic configuration at JSON schema v1. Migrate the legacy
line-format keys `markdown_filter` → `filter` and `streaming_budget` →
`streaming_buffer`. 0.9.2 deletes `memory_budget`, which has no runtime-key
replacement. Set static `markdown_limits conversion_memory=<size>` when
operators require that limit. Note that `max_inflight` is not a dynconf
runtime key in either 0.9.1 or 0.9.2 — the module rejects it as an unknown
key in both versions. Configure the bound with the static
`markdown_limits max_inflight=` directive instead.

```text
# BEFORE
schema_version=0.9
markdown_filter=on
streaming_budget=16m
memory_budget=64m
```

```json
{
  "schema_version": 1,
  "filter": "on",
  "streaming_buffer": 16777216
}
```

The watcher accepts only JSON v1. It rejects legacy line-format files and does
not change the active or last-known-good snapshot.

The JSON contract is fail-closed: unknown keys, duplicate keys, unsupported
schema versions, invalid types, and out-of-range values reject the complete
candidate and preserve the active or last-known-good snapshot. Operators
should validate the JSON shape and supported keys before deployment and verify
`configuration.dynconf` plus
`nginx_markdown_dynconf_reloads_total{reason=...}` after the next poll.

### Diagnostics JSON schema v2 migration

The diagnostics response now declares `schema_version: 2`. Consumers moving
from 0.9.1 must replace the old `config_snapshot`, `metrics_snapshot`,
`dynconf_state`, `streaming_config`, and profile-oriented sections with the
current `configuration` and `runtime` contract:

| 0.9.1 field | 0.9.2 field or action |
|-------------|------------------------|
| `config_snapshot` | `configuration.static_digest`, `configuration.effective`, and `configuration.effective_sources` |
| `metrics_snapshot` | `runtime.module_metrics` (required by the diagnostics schema) |
| `dynconf_state` | `configuration.dynconf`, including `masked_keys` |
| `streaming_config` / old `effective_config` | `streaming_config.policy` and `streaming_config.policy_source` are removed. Use `configuration.effective` and `configuration.effective_sources` |
| `profile`, `overridden_fields`, `forced_fields` | Removed with profile presets |

Validate the version before reading the response. The exact v2 contract lives
in [`schemas/diagnostics.schema.json`](../../schemas/diagnostics.schema.json).

Malformed, unknown, and excessively deep `Content-Encoding` chains follow
`markdown_error_policy`. Only `pass` forwards the original response.

### Trusted forwarded-hop behavior

`markdown_trusted_proxies` applies only to HTTP forwarded URL headers. For a
request from a trusted peer, the module processes aligned `Forwarded` or
`X-Forwarded-*` chains from right to left. It strips trusted proxy hops and
uses the first untrusted hop for the client-facing value. If every hop matches
a trusted proxy, the module discards the forwarded set. Bracketed IPv6
literals such as `[2001:db8::1]` can match a trusted CIDR. Bracketed IPv4
literals such as `[192.0.2.1]` never match. The module discards malformed or
mismatched lists as a whole.

### Prometheus Metrics v1

0.9.2 freezes the Prometheus text 0.0.4 contract at twelve metric families
with bounded label cardinality. The canonical registry is
[`schemas/metrics-v1.registry.json`](../../schemas/metrics-v1.registry.json),
the production renderer is
`components/nginx-module/src/ngx_http_markdown_metrics_v1_renderer.h`, and
the Rust/C conversion metrics cross the generated converter header boundary
before the C snapshot and renderer consume them. The operator-facing family
and label mapping lives in
[`prometheus-metrics.md`](../guides/prometheus-metrics.md). These sources and
their tests must change together. Legacy per-path, profile, and
unbounded request dimensions are not part of v1.

### Removed OTel Surface

The 0.9.2 release removes the experimental `markdown_otel` /
`markdown_otel_endpoint` directives and their implementation. Deployments
that need tracing should use NGINX's native OTel integration or another
external observability layer. The 0.9.1 behavior survives only in historical
migration material.

### Profile Presets Removed

The 0.9.2 release removed the `markdown_profile` directive and its
`balanced` / `strict_cache` / `streaming_first` presets. Express the
equivalent behavior with explicit `markdown_limits` keys. See
[MIGRATION-0.9.2.md](../guides/MIGRATION-0.9.2.md).

### `REJECT_STATUS` Action Renamed (Internal)

The 0.9.2 release renamed the C action `NGX_HTTP_MD_ACTION_REJECT_502`
to `NGX_HTTP_MD_ACTION_REJECT_STATUS`. The change is internal and has no
configuration impact.

### Backward-Compatibility Commitment

After 0.9.2, all 1.x releases maintain backward compatibility for a
minimum of 24 months.

### Dynconf File Restore

The diagnostics endpoint is read-only (`GET`/`HEAD`) and does not expose a
runtime rollback action. Restore a previous valid dynconf file by writing it to
a temporary file and atomically renaming it over the watched path. Atomic
rename ensures readers see a complete old or new file, but each worker has its
own watcher cycle and may converge on a different `config_version` briefly.
The normal poller validates and promotes that file. An invalid file leaves the
active last-known-good snapshot unchanged. Verify convergence with diagnostics
or request behavior, and use a controlled NGINX reload for a strong
synchronization boundary. See
[DYNAMIC_CONFIG.md](../guides/DYNAMIC_CONFIG.md).

### Release rollback compatibility

Rolling back the module binary alone is not sufficient. Because 0.9.2 is a
breaking configuration release, first restore a configuration compatible with
the target 0.9.1 (or 0.9.0) binary: remove 0.9.2-only directives, restore any
target-release directive names and contexts, and migrate the dynconf file to
the target schema. Then install the target module, run `nginx -t`, and restart
NGINX. Keep the 0.9.2 configuration and module together until the target
configuration has passed its own validation.

### Public Surface Inventory and Drift Detection Gate

A new release gate validates the public API source metadata and ABI drift —
directive names, defaults, syntax, status, and migration targets, dynconf
key names, types, allowed values, defaults, and inheritance, metric names,
types, labels, order, and bounded-cardinality declarations, reason codes,
and Rust/C FFI prototypes and ABI — against the declared inventory. The
detector reads live C and Rust source metadata. It does not execute
directive parse/merge functions, dynconf apply paths, or runtime metric
rendering. Runtime behavior remains verified by the existing unit,
integration, and E2E test suites. This gate runs as part of
`make release-gates-check-092` and catches accidental surface metadata and
ABI changes before they reach a release.

### Release Gates 0.9.2

The `release-gates-check-092` Make target provides the current blocking 0.9.2
release gate:

```bash
make release-gates-check-092
```

The canonical subset runs the current feature-oriented contract and focused
0.7.0/0.8.0 compatibility regressions. It evaluates the provenance-bound 091
and 092 performance baselines as inputs to one current gate. It does not call
an obsolete 0.9.0/0.9.1 wrapper chain. The full target then adds candidate-
bound artifact, fuzz, soak, documentation, and property evidence. The tag-only
`release-gate` uses the same candidate-bound contract in its controlled
AlmaLinux runtime. Any failure prevents publication.

The canonical candidate baseline is
`perf/baselines/module-baseline-092.json`. The existing workflow tooling
must finalize it from the retained `module-baseline-092-raw.json` and probe
artifacts, with the source commit, workflow run, artifact digest,
measurement timestamp, and environment identity bound in `baseline_policy`.
The file is not a release claim by itself. Tag, package, checksum, and GitHub
Release publication remain pending until all blocking gates pass.

For dynconf reload E2E, PID resolution has three outcomes: verified PID,
missing PID source (safe watcher polling), or configured-but-invalid source
(failure). `NGINX_PID_PREFIX` adds a constraint after the watcher verifies
the NGINX master identity and cannot authorize an unrelated process.

## Upgrade

See [MIGRATION-0.9.2.md](../guides/MIGRATION-0.9.2.md) for the directive
before/after examples and [UPGRADE-TO-0.9.2.md](../guides/UPGRADE-TO-0.9.2.md)
for detailed upgrade instructions by deployment method. Configurations using
any removed directive need updating before you replace the module binary.
`nginx -t` fails with `unknown directive` until the migration is complete.

**Quick upgrade (prebuilt Debian/Ubuntu x86_64 module):**

The commands below target Debian/Ubuntu x86_64 and the standard Debian module
directory. For RPM-based or aarch64 systems, select the matching artifact and
module path from [PACKAGE_INSTALLATION.md](../guides/PACKAGE_INSTALLATION.md).
Do not reuse the x86_64 filename or `/usr/lib/nginx/modules` path blindly.

> **Do not copy the module over the running one in place.** Old workers keep
> the previous file mapped. Overwriting it can serve mixed or stale code and
> risks SIGBUS on some platforms. Always stop NGINX, stage the new module
> beside the running one, atomically rename it into place, then start —
> exactly as [UPGRADE-TO-0.9.2.md](../guides/UPGRADE-TO-0.9.2.md) walks through
> step by step. You must complete and validate the migration steps below
> with `nginx -t` before the swap.

```bash
# 1. Back up the current module (the upgrade flow backs up only the module
#    binary; back up the active nginx.conf separately before migrating)
sudo cp /usr/lib/nginx/modules/ngx_http_markdown_filter_module.so \
    /usr/lib/nginx/modules/ngx_http_markdown_filter_module.so.0.9.1.bak

# 2. Migrate the 0.9.1 configuration before replacing the module
#    (see MIGRATION-0.9.2.md for before/after examples).
#    Validate with the currently loaded (old) module first:
sudo nginx -t   # must pass before continuing

# 3. Stop NGINX; the swap chain below runs only when every prior step
#    succeeds (fail-fast, set -e style chaining):
sudo systemctl stop nginx \
  && sudo install -m 0755 ngx_http_markdown_filter_module-0.9.2-nginx<nginx-version>-<os>-x86_64.so \
     /usr/lib/nginx/modules/.ngx_http_markdown_filter_module.so.0.9.2.new \
  && sudo mv /usr/lib/nginx/modules/.ngx_http_markdown_filter_module.so.0.9.2.new \
     /usr/lib/nginx/modules/ngx_http_markdown_filter_module.so \
  && sudo nginx -t \
  && sudo systemctl start nginx

# The final nginx -t validates the migrated configuration against the
# staged 0.9.2 module; NGINX starts only when stop, install, move, and
# validation all succeeded. If any step fails, restart NGINX manually
# only after inspecting the error (the old module may still be in place).
```

## Known Issues

No known release-blocking issues in the current candidate. The team resolved the historical streaming header-filter `NGX_AGAIN` divergence (decision ③-A) pre-freeze (2026-08-16). The section below documents the fix.

## Resolved During 0.9.2 Development — Streaming header-filter NGX_AGAIN semantics (decision ③-A, 2026-08-16)

Earlier 0.9.2 builds treated a downstream `NGX_AGAIN` from
`ngx_http_next_header_filter` on the streaming commit path as *retry
pending*: the commit latches rolled back and the downstream header filter
was re-invoked on resume, re-running intermediate filters (for example
gzip) that are not idempotent.  The fail-open passthrough and full-buffer
paths already followed the canonical NGINX core model (`NGX_AGAIN` =
headers queued by the write filter, no re-entry).  The two
interpretations were mutually exclusive and coexisted in the same request
lifecycle.

**Resolution (2026-08-16)**: all header-forwarding paths (streaming commit,
fail-open passthrough, pass-through bypass, full-buffer conversion output,
header-phase fail-open) now follow the canonical model — a header-chain
`NGX_AGAIN` means the write filter accepted the header block.  Commit
latches publish immediately on acceptance, the module invokes the header
chain at most once per request, and backpressured body output resumes
through the body filter chain on the write event.  The unification removes
`headers_pending` and the header-retry re-entry path.  Harness rule 69
documents the unified contract.
