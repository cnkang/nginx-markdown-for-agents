# 0.9.2 observation freeze policy

This policy is a preparation artifact. It becomes effective when the user
starts the observation phase and records the candidate identity and start date.

## Permitted change classes

During the freeze, maintainers may land a security fix,
dependency-security fix, crash fix, response-correctness fix, resource-runaway
fix, or host-compatibility fix. The associated regression test, artifact
rebuild, documentation update, and evidence refresh are part of the same
change. Maintainers may adjust a required toolchain or package when that
adjustment delivers one of those fixes.

Every permitted change receives a new source identity, focused verification, and an observation-segment boundary. The previous evidence remains immutable.

## Deferred change classes

Defer new features, routine refactors, output prettification, optional architecture changes, and non-essential dependency upgrades. Do not use the freeze to restore removed dynconf, selector, wildcard, profile, or remote-control surfaces.

## Exception process

An exception request records the problem and the evidence that the deferred
change is necessary. It also records alternatives, migration cost, affected
contracts, focused and broad reruns, and the proposed observation-segment
boundary. The decision owner approves or rejects the exception. Approval does
not waive ABI, schema, security, or rollback checks.

This document intentionally does not identify an immutable last breaking release. The candidate and each permitted change are bound to their actual source and working-tree identities.
