# Release Notes: 1.0.0-rc.1

**Status**: Release candidate. Not yet published.

**Target release date**: TBD (at release)

The latest public stable release is v0.9.4. The project has not published the
1.0.0-rc.1 candidate yet. No tag, GitHub Release, or package publication exists
for the candidate.

**Compatibility target**: The 20 active directives and their defaults, the HTTP
representation, the metrics and diagnostics contracts, the reason codes, and
the Rust/C FFI ABI version 3 stay compatible with v0.9.4. The candidate adds
release tooling and packaging support. It does not change runtime behavior.

---

## Summary

The candidate prepares the 1.0 line in two areas.

- A blocking cross-release contract gate compares a candidate against frozen
  manifests of the published v0.9.2 and v0.9.4 releases. It covers directives,
  metrics, reason codes, diagnostics, the bound HTTP tests, packaging, and the
  FFI ABI. A coordinated edit of the implementation and the current inventory
  no longer passes without a decision.
- The packaging path maps one SemVer release identity onto Debian and RPM
  package versions. A prerelease sorts below its final release in both package
  families.

The candidate does not add a directive, change a default, or alter the
response format.

## Release identity

| Item | Value |
|---|---|
| Release identity | `1.0.0-rc.1` |
| Debian upstream version | `1.0.0~bdudfaababfa` |
| RPM version | `1.0.0~bdudfaababfa` |
| RPM release | `nginx1.28.3.1` |

The tilde keeps the prerelease below the final `1.0.0` release in both package
families. The letter-only encoding also preserves SemVer order inside the
prerelease identifiers. `make package-version-ordering-check` proves the
mapping with the real Debian and RPM tools.

## Compatibility gate

The gate has these entry points.

| Command | Purpose |
|---|---|
| `make compatibility-contract-check` | Verify the anchors and compare the working tree |
| `make compatibility-contract-tests` | Run extraction, comparison, and negative fixtures |
| `python3 -m tools.compatibility verify-anchors` | Verify the anchors only |

The comparator returns `OK`, `ADDITIVE`, `REVIEW_REQUIRED`, `BREAKING`, or
`UNVERIFIED`. The last three block a bare run. An approval file can waive one
exact review finding. It cannot waive a breaking finding.

## Candidate status

The candidate needs release-time evidence before publication.

- The artifact-only rehearsal must run on the candidate commit.
- The protected signing rehearsal needs the `release-signing` environment.
- The approved candidate SHA must match the tag commit.
- The repository must confirm its immutable-release setting for a prerelease
  asset upload.

## Packages and upgrade path

The candidate produces the same package families as v0.9.4. An install over
v0.9.4 must keep the module ABI and the configuration contract. Package
metadata uses the mapped prerelease version, so `dpkg` and `rpm` keep the
candidate below the final 1.0.0 package.

Do not treat this candidate as a stable release. Use v0.9.4 for production
deployments until the project publishes the 1.0.0 release.
