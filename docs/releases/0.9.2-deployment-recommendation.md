# 0.9.2 deployment recommendation

For the pre-LTS candidate, run the Markdown conversion module in a dedicated
NGINX instance or container. Keep conversion traffic and its resource limits
separate from general web serving so operators can observe conversion-specific
RSS, CPU, file descriptors, in-flight requests, and tail latency. The
[capacity analysis artifact](../../artifacts/release/0.9.2/capacity-analysis.json)
must contain measured values. Operators must collect those values before they
treat resource defaults as production limits.

Use the normal NGINX process model and the retained full-buffer and streaming
engines. This recommendation does not add thread pools, an async or plugin
rewrite, profiles, OpenTelemetry, per-path shadow traffic, or a remote-write
control plane. Those surfaces are outside the 0.9.2 convergence contract.

## Separate the lifecycle steps

Keep these operator actions separate and record each result against the same
candidate identity:

1. **Build** the module from the pinned source and dependency inputs. The build
   must write to a temporary prefix and must not modify the running NGINX.
2. **Install** the module and its supporting files atomically into the selected
   instance or image. Verify the artifact and capability report before making
   it available to the service.
3. **Enable** the module by adding the `load_module` and Markdown directives to
   the instance configuration. Run `nginx -t` and retain its output.
4. **Restart** the instance and verify that the running process loads the new
   module. A successful configuration reload alone does not prove module
   replacement. Rollback uses the same atomic replace and verified restart
   sequence documented in
   [the upgrade and rollback contract](./0.9.2-upgrade-and-rollback.md).

Keep the prior module, configuration, and generated contract artifacts until
the restart and smoke checks pass. Do not perform an in-place hot replacement
or reuse an incompatible metrics shared-memory layout.

## Initial operating boundary

Start with the documented full-buffer default for locations that do not
explicitly opt into streaming. Enable streaming only after operators check its
cache and response-integrity requirements, including the conflict between
`markdown_streaming force` and `markdown_cache_validation full`.
Use the capability check to fail explicitly when either engine or one of the
five retained encodings is unavailable. Do not report full support after a
silent downgrade.

Treat the initial limits as provisional. The user-owned observation plan must
measure worker occupancy, per-request peak memory, old/new worker overlap,
reclaim timing, and tail latency under mixed load before those limits support
an LTS decision.
