# 0.9.3 Deployment Recommendation

This note gives the recommended deployment pattern for 0.9.3. 0.9.3 is not yet
published, so apply it after the release. It is a recommendation, not a
requirement.

## Recommended order

1. **Pilot one host per platform family.** Use one nginx.org host and one
   Ubuntu-native host. Confirm the Markdown response, the HTML response, and
   the `Vary: Accept` header on each host.
2. **Run the doctor on every pilot host.** A mismatch between the module and
   the NGINX binary shows here before a reload.
3. **Reload, do not restart.** A reload keeps the worker connection handling
   smooth and applies the new module after the new workers start.
4. **Watch one release cycle.** Compare the module metrics and the error log
   with the previous module version.
5. **Roll out to the remaining hosts.** Apply the same artifact family on each
   host. Do not mix the nginx.org package with the Ubuntu-native package.

## Hosts that need extra care

| Host | Reason | Action |
|---|---|---|
| Ubuntu host with automatic security updates | A revision change can change the ABI | Pin the module version, and read the NGINX changelog before an upgrade |
| Host with a custom NGINX build | No prebuilt artifact matches the build | Build from source for the exact version |
| Host with streaming and decompression enabled | Response shape depends on the codec chain | Repeat the compression checks from the 0.9.2 baseline |
| Host behind a CDN | `Vary: Accept` controls cache correctness | Confirm that the CDN keeps separate variants |

## Not recommended

- Copying a module file between hosts with different NGINX revisions.
- Loading the module in a configuration that sets `markdown_filter on` before
  the pilot check.
- Rolling back across an ABI change without a rebuild.
