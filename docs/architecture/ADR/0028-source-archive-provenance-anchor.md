# ADR-0028: Source-Archive Provenance Anchors on the Commit, Not the Tag Archive

## Status

Accepted

## Date

2026-09-12

## Context

The 0.9.2 release records where its source came from. The first implementation
stored a SHA-256 digest of the GitHub tag archive in
`packaging/source-archive-digests.sha256`, then required every tag release to
find its own entry there and fail closed when it was missing.

No implementation can satisfy that requirement. The registry file is part of the tree, so
committing an entry changes the tree, and GitHub generates a tag archive from the
tree at that tag. No one can therefore record an entry describing a tag's own archive before
the tag exists, and the digest recorded afterwards never matches
the archive the tag produces. Two independent reviews reached this conclusion
independently, and the digest requirement in the release-manifest validator had
to make the digest optional as a consequence.

Making the digest optional traded one defect for a worse one: a tag release could
publish a manifest that claimed an available source archive while carrying no
cryptographic provenance at all. That gap was found again by four independent
sources in the pre-freeze review, with one of them calling the release unready on
it alone.

## Decision

- The provenance anchor is the **commit identity**, and the release workflow
  derives the source artifact from it. During a tag release the workflow builds a
  canonical source bundle with `git archive --format=tar` from the released
  commit, piped through `gzip -n`. The commit fixes every entry's timestamp and
  `gzip -n` drops the archive name and timestamp, so the same commit always
  produces the same bytes whatever day the run happens.
- The manifest records that bundle's SHA-256 and its release URL, and the workflow publishes the bundle next to the other release assets and
  lists it in `SHA256SUMS` before signing. The chain is self-contained: immutable commit to workflow-built bundle
  to SHA-256 to manifest to signed checksums.
- The validator **requires** `source.sha256` for tag releases, and the release
  step fails before publication when the bundle step produced no digest. A manifest without a digest can no longer reach a release.
- The registry under `packaging/` becomes an **audit record**. When an entry
  exists, the release step compares it with the digest computed for the release
  and fails on disagreement, so the two records cannot drift apart silently. Its
  absence no longer blocks a release, and this comparison replaces the previous
  `::warning::` that let one through.
- No document claims that a later release of the same tag reads the registry. A
  rerun of a tag checks out that tag's tree and cannot see a commit made after it,
  so the claim was never satisfiable.

## Consequences

- Provenance no longer depends on the byte stability of an archive generated by
  the hosting service: the workflow builds and hashes the artifact it publishes.
- A same-tag rerun rebuilds the same bundle from the same commit and therefore
  records the same digest, which is the property the withdrawn registry claim was
  trying to obtain.
- Reviews that expect a fail-closed digest check at tag time now find one, and
  `packaging/scripts/test_release_manifest.py::test_tag_missing_source_sha_is_rejected`
  covers the validator's rejection path.
- The registry keeps its audit value: it records what was actually published, and
  a mismatch is now an error rather than a silent difference.
