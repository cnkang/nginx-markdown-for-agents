# 1.0.0-rc.1 Implementation Plan

This plan records the release-candidate work for the 1.0 line. The candidate
builds on [1.0.0-week1-implementation-plan.md](1.0.0-week1-implementation-plan.md)
and [1.0.0-week1-results.md](1.0.0-week1-results.md). The release verdict is
[1.0.0-rc1-readiness.md](1.0.0-rc1-readiness.md).

The 1.0.0-rc.1 candidate is not yet published. v0.9.4 remains the latest
public stable release.

## Scope

The candidate closes the release-identity and validator gaps from the Week 1
record.

| Task | Deliverable |
|------|-------------|
| R1 | Release identity raised to `1.0.0-rc.1` across source, chart, workflow, and tooling defaults |
| R2 | One SemVer grammar for release-time validators |
| R3 | Release-matrix artifact paths derived from the package manifest |
| R4 | Ubuntu-native package metadata mapped through the prerelease mapper |
| R5 | Candidate release notes, upgrade, rollback, migration, and deployment documents |
| R6 | Current NGINX source checksums for 1.30.8 and 1.31.10 |

The candidate does not change a directive, a default, the HTTP representation,
the metrics or diagnostics contract, the reason codes, or FFI ABI version 3.

## Release identity

Release identity surfaces carry `1.0.0-rc.1`. Schema artifacts use numeric
version `1.0.0`.

| Surface | File |
|---------|------|
| Package version | `components/rust-converter/Cargo.toml` |
| Internal dependency versions | `components/rust-converter/fuzz/Cargo.toml`, `tools/corpus/test-corpus-conversion/Cargo.toml` |
| Chart version and app version | `charts/nginx-markdown/Chart.yaml` |
| Release identity | `Makefile` `RELEASE_LINE` (`1.0.0-rc.1`) |
| Schema artifact line | `Makefile` `SCHEMA_RELEASE_VERSION` (`1.0.0`) |
| Release workflow | `.github/workflows/release-packages.yml` `RELEASE_VERSION` |
| CI release contract | `.github/workflows/ci.yml` |

`tools/lib/semver.py` provides the release-version grammar. Schema artifacts
use the numeric `1.0.0` line. Schema tools reject prerelease arguments such as
`1.0.0-rc.1`. Soak, qualification, reason-code, and release-metadata tools
accept the candidate identity where applicable.

## Candidate evidence

The candidate needs release-time evidence for the exact commit.

| Evidence | Producer |
|----------|----------|
| Package set | Artifact-only rehearsal of `release-packages.yml` |
| Signed checksums and packages | Protected `release-signing` rehearsal |
| Compatibility records | Rehearsal jobs under `docs/evidence/1.0.0-rc.1/compat/` |
| Real-NGINX gates | Release Candidate Gates workflow |

The local `make release-gates-check-094` target fails at the compatibility
evidence step until those records exist. That failure is honest. It does not
indicate a contract defect.

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| The artifact-only rehearsal needs a dispatched workflow | Local checks cannot produce the evidence | Run the rehearsal on the candidate commit before the tag |
| The signing environment needs a reviewer | Signing stays unverified locally | Schedule the protected rehearsal with a maintainer present |
| A prerelease asset upload may need a draft release | Publication could fail late | Confirm the repository immutable-release setting before the tag |
| The RC evidence directory is empty until the rehearsal | The local release gate stops at the evidence step | Record the rehearsal output, then re-run the gate |
