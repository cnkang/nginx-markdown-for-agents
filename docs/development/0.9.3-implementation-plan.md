# 0.9.3 Compatibility Maintenance Implementation Plan

**Status**: In progress — release candidate preparation
**Baseline**: `b8677102` (`main`, `origin/main`, 2026-10-29)
**Working branch**: `release/0.9.3-nginx-ubuntu-compat`
**Target**: v0.9.3 compatibility maintenance release (non-breaking)

This plan records the audit that produced the 0.9.3 work items, the design
choices behind them, and the evidence each item must produce. It contains no
release claim: the tag and the GitHub Release belong to the separate release
stage. See `docs/releases/0.9.3-release-notes.md` for the publication-state
rules.

## 1. Purpose

v0.9.2 (published 2026-10-08) was the last planned breaking release before
v1.0. v0.9.3 is a controlled compatibility maintenance exception. The release
does four things:

1. Make the current nginx.org stable and mainline releases real, release
   blocking targets with published artifacts.
2. Add Ubuntu 24.04 LTS and Ubuntu 26.04 LTS native NGINX to the supported
   surface, using Canonical's source package and ABI, not an nginx.org build.
3. Separate four compatibility contracts that the current tooling mixes:
   source floor, upstream official binaries, distro-native compatibility, and
   actual release-asset availability.
4. Give maintainers a repeatable promotion path that cannot mark a version
   supported without recorded evidence.

## 2. Non-Goals

The release does not:

- add, remove, rename, or re-default any of the 20 active NGINX directives.
- change the HTTP representation, metrics, diagnostics, reason-code, or
  Rust/C FFI contracts.
- restore dynconf or OTel.
- rewrite the streaming state machine.
- raise the minimum NGINX source version (`>= 1.24.0` stays).
- change the Rust toolchain or MSRV (`1.98.1` / `1.98` stay).
- publish a stable tag in this stage.

The maintainer allows a C or Rust runtime change only after a reproduced
incompatibility exists. The change must be the smallest fix, and it needs a
production call-path test.

## 5. Design Decisions

### D1. Promotion is a separate, evidence-gated operation

Add `tools/release/matrix/promote_matrix.py`. It reads machine-readable
evidence records, refuses to promote on a missing or inconsistent record, and
writes the policy matrix plus the generated projections. Auto-discovery keeps
its current rule: new versions enter as `best-effort` / `pending`.

`promote_matrix.py`:

- takes one or more `--evidence` files and a `--version`.
- validates every required field and every cross-check in the evidence
  contract (section 6).
- promotes only rows whose `(version, os, libc, arch, artifact_type)` matches a
  verified evidence record.
- demotes superseded patches of the same minor track unless
  `--keep-previous` is given.
- never modifies a row with `managed_by: manual`.
- supports `--dry-run` and `--check`, and is idempotent.

### D2. Evidence contract

One JSON record per verified target, stored under
`docs/evidence/0.9.3/compat/<target-id>.json`. Required fields:

```text
target_identity,
source_kind (nginx.org | ubuntu-default-repo | container-registry),
nginx_version, nginx_package_revision, distro, distro_version, arch,
libc, abi_provide, source_reference, source_digest,
build_args_digest, module_sha256, rust_version, features,
tests (list of name/status), pass, fail, skip,
workflow_run_url, commit_sha, date, verified_by
```

A `container-registry` record also carries `image_reference`,
`image_digest` and `built_image_id` (see 11.3).

`validate_compatibility_evidence.py` enforces the contract and binds each
record to a matrix row. `supported` rows must name a record. A `verified` row
requires a record with `fail == 0`, `skip == 0`, and at least one `PASS` per
required test class (build, load, request, lifecycle).

### D3. Ubuntu-native artifacts are separate artifacts

The distro build gets its own package name,
`nginx-module-markdown-for-agents-ubuntu`, its own dependency on the distro
ABI virtual package (`nginx-abi-<version>-1`), and its own asset name
(`..._0.9.3-1ubuntu24.04.1_amd64.deb`). It carries `Conflicts:` against the
nginx.org package because both own
`/usr/lib/nginx/modules/ngx_http_markdown_filter_module.so`.

The module is built from the matching Ubuntu source package revision. The build
uses the `nginx -V` configure arguments. A tokenizer parses the arguments, and
a shell never evaluates them.

### D4. Brotli

The module's Brotli support follows the host distribution when the host
package carries the decoder fix. The nginx.org artifact stays statically
bundled, because its build base has no fixed package. The Ubuntu package
records the `libbrotli1` version it linked and depends on it, so Ubuntu
security updates reach the decoder.

### D5. Superseded patches are demoted, not deleted

A superseded patch of a supported track keeps its row, its published
artifacts, and its evidence. The row moves to `best-effort` with
`release_blocking: false`. Deleting the row would erase the record that the
version once shipped and would hide the upgrade path from users.

### D6. Long-term baselines stay release blocking

1.24.0 (compatibility floor), 1.26.3, and 1.28.3 keep `supported`,
`release_blocking: true`, and a prebuilt artifact for both architectures.
nginx.org still serves all three, and dropping them would remove artifacts
that users install today.

### D7. Release blocking means the DAG waits

A workflow job consumes every row with `release_blocking: true`, and the
publication job depends on that job. A flag without a dependency edge is a policy
violation, checked by `validate_workflow_matrix_consumers.py`.

### D8. No second source of truth

The support matrix stays in `tools/release-matrix.json`. The contract
projection, documentation tables, package workflow inputs, and installer
matrix all derive from it. `packaging/matrix.yaml` now points at the canonical
file so it cannot drift again.

## 7. Compatibility Matrix Policy

Four contracts, four owners, four kinds of evidence:

1. **Source compatibility floor** — `>= 1.24.0`. The project supports a source build. It is not a binary promise.
2. **Upstream official binaries** — nginx.org version, official build
   arguments, DEB/RPM and musl tarballs. Verified per version, per
   architecture, per libc.
3. **Distro-native compatibility** — bound to the Ubuntu release, the exact
   package revision, the source patchset, the ABI provide, and the host
   evidence. A distro revision change reopens the row for review.
4. **Actual release-asset availability** — what a given tag published. The
   matrix says what the next release intends to build, not what an old tag
   contains.

Rows move only through `promote_matrix.py` and only with evidence.

## 8. Risks

| Risk | Impact | Control |
|------|--------|---------|
| Ubuntu source revision moves during the release | Evidence records a revision that no longer installs | Evidence stores the revision. The guide states the tested revision and date. The validator compares the recorded revision with the row. |
| Ubuntu security update changes the module ABI | An installed module fails to load after `apt upgrade` | The package depends on the ABI virtual package, so apt refuses the module after an ABI change. The guide documents the fail-closed path. |
| amd64 emulation produces a false pass | Weak evidence for the x86_64 targets | Emulated runs are marked in the evidence. The release workflow runs native amd64 runners. |
| Distro Brotli is older than the fix | Reintroduced decoder CVE | The distro build records the linked Brotli version and depends on the distro package. The release notes name the condition. |
| Superseded patch demotion surprises users | No 0.9.3 artifact for 1.30.5 | Release notes state the current patch targets and point at v0.9.2 assets. |
| Two documentation matrices disagree | Contradictory support claim | The release gate compares both generated sections against the matrix. |

### 11.1 Every release-blocking row has a CI producer

local record. The release workflow now has a CI producer for all 48:

| Family | Rows | CI producer |
|--------|------|-------------|

The workflow defines these producers, but no release workflow run has
verified them yet. Until a run does, the coverage exists only on paper.

1.30.4 stays supported and blocking because the checked-in perf baselines

A demotion leaves the perf gate with nothing to run. `matrix-promote` passes

### 11.2 Checked-in evidence cannot carry the tag commit SHA

Status: [release workflow run 41038678241](https://github.com/cnkang/nginx-markdown-for-agents/actions/runs/41038678241)
verified the CI evidence path for candidate SHA
`d99f45b94ad434d72b0bfebedb5a001dfd5336d6`.
The workflow staged 48 records and ran the validator with `--require-ci`,
`--require-blocking`, `--candidate-sha "${GITHUB_SHA}"`,
`--workflow-run-url`, and the staged `--evidence-dir`. The validator completed
successfully and the release gate continued to later checks. This resolves the
CI evidence handoff in issue #310. The overall Release Gate job later failed
because the release metadata still marks 0.9.3 Unreleased. This evidence run
does not establish release readiness or authorize a tag. A different candidate
SHA requires a new evidence run.

An operator builds a record before committing it, so its `commit_sha` names
the build commit. The commit that contains the record is always a child of
that commit, so a checked-in record can never name the tag commit. The 12
checked-in records also name `local:release-agent`, so `--require-ci` rejects
them. Relabeling a local record does not change who produced it, so the gate
must read records that a CI job produced in the same run.

The release workflow now implements that path:

1. Each producer writes one record for the run's own artifact. The record
   carries `commit_sha` set to `github.sha`, `workflow_run_url` set to this run,
   and `verified_by` set to `ci:<workflow>/<job>`.
2. Each record has a unique file name that carries its identity, and each one
   goes into its own `compat-evidence-<identity>` artifact. Package
   downloads that merge `pkg-deb-*` no longer carry a record.
3. `release-gate` downloads `compat-evidence-*` without `merge-multiple`.
   `tools/release/matrix/stage_compatibility_evidence.py` copies one regular
   `.json` file from each artifact into a fresh directory. It rejects
   symlinks, nested directories, stray files, unsafe names, records that
   resolve outside their artifact, duplicate names, and an empty download.
4. The gate runs `validate_compatibility_evidence.py` with
   `--evidence-dir` at the staged directory, `--require-ci`,
   `--candidate-sha "${GITHUB_SHA}"` and `--workflow-run-url`. The last option
   rejects a record from another run. Tag runs add `--require-blocking`.

The gate never reads `docs/evidence/0.9.3/compat/`. The checked-in records
stay as local pre-verification, and `make compatibility-evidence-check`
still validates them. Their build commit is `035cda2c`, which precedes the
streaming write batching change. The records of the candidate run supersede
them for publication.

A maintainer pushes the tag only after the candidate is frozen, so a tag run
cannot be the first proof. The `require_blocking` input of a manual dispatch adds
`--require-blocking` to the same gate. A dispatch with `require_blocking=true`
on the candidate branch is the proof run. Run 41038678241 verified the evidence
path for `d99f45b94ad434d72b0bfebedb5a001dfd5336d6`. Its later release metadata
failure is separate from this evidence check. Resolve release metadata checks
before publishing.

### 11.3 Container rows have a container-registry record

Status: implemented. No end-to-end run has verified it yet.

The evidence contract has a `container-registry` source kind. A container
record must carry `image_reference`, `image_digest` and `built_image_id`. The
digests use the `sha256:<64 hex>` form. A record covers a `docker-image` row
only when the row's `image_ref` and `image_digest` both match. A moved tag or
a rebuilt base therefore never covers the row. nginx.org and Ubuntu records
still never cover a container row.

The `build-and-verify` job in `official-nginx-docker.yml` builds the image on
the pinned base digest. It runs the existing functional check, and then runs
`verify-nginx-org-module.sh` inside the built image. The job writes a record
for the module that it copies out of that image. The job loads the image locally
and never pushes it, so `built_image_id` is its content-addressed ID.

The release workflow calls this workflow in `official-docker-release-gate`.
That job used to wait for `release-gate`, but `release-gate` now reads the
container records, so the old order would form a cycle. The job now waits only
for `prepare` and `fuzz-qualification`, and `release-gate` waits for it.
`publish` still waits for both jobs.

### 11.4 amd64 nginx.org evidence is emulated

The four amd64 nginx.org records carry `"execution_environment": "emulated"`.
They were built and loaded under user-mode emulation on an arm64 host. The
native x64 node could not fetch the pinned AlmaLinux base image. Its Docker
registry mirror refused the digest, and the node's GitHub access reset the
Brotli tarball download. These checked-in records remain local
pre-verification. The CI records that the release gate reads come from native
runners: every producer checks that the runner architecture matches the row.

### 11.5 Ubuntu revision drift

`1.24.0-2ubuntu7.19` and `1.28.3-2ubuntu1.12` were current on 2026-10-29. A
newer security revision reopens the row. The record names the revision, so the
gate reports the mismatch instead of accepting the old evidence.

### 11.7 The `0.9.2 Contract Gates` check name

The required status check on `main` keeps its published name. renaming it would
