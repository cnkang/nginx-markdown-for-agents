### Packaging delta

The release matrix moved from 71 rows to 43 rows. Two kinds of change appear.

- Twelve distro-specific rows for the 1.30 and 1.31 branches disappeared. Those
  branches stay supported through the nginx.org tarball channel, and the
  distro-specific rows no longer list them.
- Four rows moved from best-effort to supported: `1.24/ubuntu-24.04` on both
  architectures, and `1.28/ubuntu-26.04` on both architectures. The comparator
  reports a promotion as additive, so those rows do not appear in the delta.

`INDEX.json` lists all thirteen non-additive finding identifiers with a
rationale. The gate fails when an observed delta is missing from that list, and
it also fails when a listed delta stops occurring.

### Provenance gaps

No historical anchor lacks a machine-readable source. The one gap is
behavioural. A static manifest cannot prove HTTP behaviour, so the HTTP surface
binds to the test files that execute the request path and records their
digests. A change to a bound test yields `REVIEW_REQUIRED` rather than a pass.

### Release matrix transition after the 1.30.8 and 1.31.10 discovery

A later `main` commit added nginx.org stable 1.30.8 and mainline 1.31.10 to the
matrix as `best-effort` with `pending` verification, and its message also
claims a removal of 1.30.7 and 1.31.9. The removal did not happen. The
authoritative matrix still carries four `supported` and release-blocking rows
for each of 1.30.7 and 1.31.9, and the generated projections list them as
supported.

That state follows the repository rule that auto-discovery never grants
support. `tools/release/matrix/validate_auto_update_policy.py` requires a
discovered version to stay `best-effort`, `pending`, and non-blocking.
`tools/release/matrix/promote_matrix.py` is the only path to support, and it
needs recorded build, load, and request evidence. No checksum for 1.30.8 or
1.31.10 exists in `packaging/nginx-checksums.yaml`, and no evidence record
covers them, so a promotion would invent a result the project does not hold.

The compatibility gate agrees with that reading. The candidate keeps every
supported target of `v0.9.4`, so the comparison reports only patch progression
for the 1.30 and 1.31 groups. Deleting the verified rows would remove eight
release-blocking entries with no verified replacement, which the gate reports
as a target or tier change.

The next maintainer action is one command once the evidence exists:

```
python3 tools/release/matrix/promote_matrix.py \
    --evidence docs/evidence/<line>/compat/<record>.json \
    --demote-superseded
```

That call promotes the new patch and demotes the superseded row to
`best-effort` instead of deleting it, which matches the 0.9.3 precedent.

## W1-03: RC Packaging and Safe Publication

### Version mapping

| Release | Debian upstream | Debian package version | RPM version | RPM release |
|---------|-----------------|------------------------|-------------|-------------|
| `0.9.4` | `0.9.4` | `0.9.4-nginx1.28.3` | `0.9.4` | `nginx1.28.3.1` |
| `1.0.0-rc.1` | `1.0.0~rc1` | `1.0.0~rc1-nginx1.28.3` | `1.0.0~rc1` | `nginx1.28.3.1` |
| `1.0.0-rc.2` | `1.0.0~rc2` | `1.0.0~rc2-nginx1.28.3` | `1.0.0~rc2` | `nginx1.28.3.1` |
| `1.0.0` | `1.0.0` | `1.0.0-nginx1.28.3` | `1.0.0` | `nginx1.28.3.1` |

The tilde carries the ordering in both families. An independent design review
proposed a release-first RPM marker, and the measured `rpmvercmp` result
rejected it. `rpmvercmp` ranks a numeric leading segment above a letter
segment, so `0.rc1.nginx1.28.3` sorts above `nginx1.28.3.1`. The shipped
mapping puts the marker in the version field instead.

### Ordering evidence

`packaging/tests/test-version-ordering.sh` proves the mapping with the real
package tools.

| Check | Tool | Result |
|-------|------|--------|
| `0.9.4 < 1.0.0~rc1` | `dpkg --compare-versions` | pass |
| `1.0.0~rc1 < 1.0.0~rc2` | `dpkg --compare-versions` | pass |
| `1.0.0~rc2 < 1.0.0` | `dpkg --compare-versions` | pass |
| naive `1.0.0-rc1` sorts above `1.0.0` | `dpkg --compare-versions` | confirmed, so the tilde is required |
| install `rc1` then `rc2` then `1.0.0` | `dpkg -i` in `ubuntu:24.04` | pass, final version is `1.0.0-nginx1.28.3` |
| `0.9.4 < 1.0.0~rc1 < 1.0.0~rc2 < 1.0.0` | `rpm.vercmp` in `rockylinux:9` | pass |
| naive release marker `0.rc1` sorts above the final release | `rpm.vercmp` in `rockylinux:9` | confirmed, so the version-field marker is required |

A host without Docker reports `NOT_RUN` for the container checks. The CI job
runs the target with `REQUIRE_ALL=1`, which turns `NOT_RUN` into a failure.

### Preserved publication guarantees

The publish job keeps its exact dependency set and its per-dependency result
guards. It still requires `release-gate`, `rc-release-gates`,
`fuzz-qualification`, `official-docker-release-gate`, `integrity-checksums`,
`integrity-signature`, `musl-build`, and `ubuntu-native`, and it still treats a
skipped signature as acceptable only on a manual dispatch. The release workflow
test suite checks that truth table on every run.

No pull-request job can reach the signing secrets. The signing jobs keep the
`release-signing` environment, and the new compatibility job requests
`contents: read` only.
