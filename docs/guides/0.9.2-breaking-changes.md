# 0.9.2 Breaking Changes Reference

**Release line:** 0.9.2 (final breaking release before 1.0)

This document is the standalone breaking-change reference for upgrading from
0.9.1 to 0.9.2. It summarizes every removed directive, its replacement, and
the impact on existing configurations. Full before/after examples and the
step-by-step upgrade path live in
[MIGRATION-0.9.2.md](MIGRATION-0.9.2.md).

---

## Overview

0.9.2 is a **breaking release**. The release reduces the configuration surface from
63 directives to exactly 25. All removed directives now produce NGINX's
standard `unknown directive` error during `nginx -t` (0.9.0/0.9.1 reject-only
stubs previously produced a migration-hint error instead).

| Category | Count | Action required |
|----------|-------|-----------------|
| Reject-only migration stubs removed | 19 | Delete the directive; it already failed `nginx -t` |
| Active directives removed | 14 | Replace with the listed equivalent |
| Directives consolidated or retired with `markdown_limits` | 5 | Convert four directives to `markdown_limits key=value` syntax; `markdown_stream_flush_min` has no replacement |
| Total retained directives | 25 | No change needed |

After 0.9.2, all 1.x releases maintain backward compatibility for a minimum
of 24 months, so this is the last planned breaking configuration change.

### Dynamic configuration file migration

The dynconf file format is frozen at JSON schema v1, and the module rejects
legacy line-format files. Detailed before/after examples and the diagnostics
`schema_version: 2` field mapping live in
[MIGRATION-0.9.2.md](MIGRATION-0.9.2.md).

- `markdown_filter` key → `filter`, `streaming_budget` key → `streaming_buffer`.
- `memory_budget` has no runtime-key replacement: configure static
  `markdown_limits conversion_memory=<size>` instead.
- The watcher rejects a legacy line-format file and keeps the active or
  last-known-good snapshot.

### Diagnostics JSON schema v2 migration

The diagnostics response declares `schema_version: 2`. The complete
0.9.1→0.9.2 field mapping is in
[MIGRATION-0.9.2.md](MIGRATION-0.9.2.md) — see the diagnostics section
there before migrating consumers.

Consumers must validate the version before reading fields. The authoritative
v2 schema is [`schemas/diagnostics.schema.json`](../../schemas/diagnostics.schema.json).

### Content-Encoding policy

Malformed, unknown, and excessively deep `Content-Encoding` chains now follow
the configured `markdown_error_policy`. Only `pass` forwards the original
response. `fail_closed` and status policies reject the response. The `deflate`
coding supported by the 0.9.2 public contract uses the zlib-wrapped RFC
1950 format. Raw RFC 1951 deflate remains supported as a compatibility
fallback for legacy servers. The decoding paths differ:

- **Full-buffer**: a zlib-wrapped (RFC 1950) decode that fails with a format
  error and zero output retries as raw RFC 1951 (`-MAX_WBITS`). A partial
  decode is never replayed.
- **Streaming**: classification relies on the first two bytes (zlib header
  present → wrapped mode) and fails closed when the bytes misclassify the
  format.
- **Rust chain decoder**: the referenced contract defines the behavior
  (`components/rust-converter/src/decompress.rs`), which documents the
  sniffing heuristic and its limits.

### Trusted proxy identity

The module accepts `markdown_trusted_proxies` only in the `http` context. When a
request arrives through a configured trusted proxy, the module evaluates the
forwarded chain from right to left, strips only trusted hops, and uses the
first remaining untrusted value as the client identity. `X-Forwarded-Proto`
accepts both `http` and `https`. The module trusts the value only across the
same configured proxy boundary. Do not treat forwarded headers as authoritative
when the direct connection peer is outside the trusted-proxy set.

## Removed Active Directives (14)

> **Compact reference.** Detailed before/after migration examples for every
> directive below live in [MIGRATION-0.9.2.md](MIGRATION-0.9.2.md). This
> table is the summary view and is not maintained as a second copy.

| Removed directive | Replacement | Impact |
|-------------------|-------------|--------|
| `markdown_profile` | Explicit directive settings (see MIGRATION-0.9.2.md for balanced/strict_cache/streaming_first equivalents) | Profile presets gone; operators must set limits explicitly |
| `markdown_metrics_format` | None — metrics always render in Prometheus text format | Remove the directive; the `markdown_metrics` endpoint format is fixed |
| `markdown_metrics_per_path` | None — per-path metrics removed (log-based path analysis) | Remove the directive and `markdown_metrics_per_path_cardinality` |
| `markdown_metrics_per_path_cardinality` | None — see `markdown_metrics_per_path` | Remove the directive |
| `markdown_buffer_chunked` | None — chunked response buffering is always enabled internally | Remove the directive |
| `markdown_streaming_shadow` | None | Shadow comparison mode removed |
| `markdown_streaming_zero_copy` | None — zero-copy output is an internal optimization | Remove the directive |
| `markdown_llm_provider` | None — token estimation uses a fixed internal ratio (keep `markdown_token_estimate`) | Remove the directive |
| `markdown_chars_per_token` | None — fixed built-in ratio of 4.0 chars/token | Remove the directive |
| `markdown_stream_types` | `markdown_stream_excluded_types` (positive allowlist becomes exclusion list; `markdown_content_types` controls conversion eligibility) | Invert the type list semantics |
| `markdown_stream_threshold` | None — threshold fixed at 1 MiB internally; chunked responses stream when `markdown_streaming` policy permits | Remove the directive |
| `markdown_diagnostics_allow` | Remove the directive. Diagnostics are loopback-only by default. Native `allow`/`deny` may narrow access | The handler rejects non-loopback peers before rendering |
| `markdown_otel` | None — experimental OpenTelemetry subsystem removed (use NGINX's native OTel module) | Remove the directive and `markdown_otel_endpoint` |
| `markdown_otel_endpoint` | None — see `markdown_otel` | Remove the directive |

## Breaking Semantic Changes

- **Migration hints removed.** Reject-only stubs in 0.9.0/0.9.1 produced a
  custom migration-hint error. In 0.9.2 they are gone. `nginx -t` reports the
  standard `unknown directive` error for every removed directive.
- **`REJECT_STATUS` action rename (internal).** The C streaming action
  `NGX_HTTP_MD_ACTION_REJECT_502` became
  `NGX_HTTP_MD_ACTION_REJECT_STATUS` to reflect that the reject status is
  policy-configurable (`markdown_error_policy status <code>`). This is an
  internal symbol rename with no configuration impact.
- **OTel subsystem removed.** The experimental `markdown_otel` /
  `markdown_otel_endpoint` surface and all OTel-related metrics, spans, and
  export paths got removed. No worker-owned OTel lifecycle exists anymore.
- **Per-path metrics removed.** `markdown_metrics_per_path` and its
  cardinality control are gone. The per-path walk disables in production
  builds.
- **Profiles removed.** Profile presets (`balanced`, `strict_cache`,
  `streaming_first`) no longer exist. All limits express through
  explicit directives (`markdown_limits`, `markdown_cache_validation`,
  `markdown_error_policy`, `markdown_streaming`, `markdown_accept`).
- **Helm chart default limits relaxed to module frozen defaults.** The
  chart previously rendered `conversion_memory=10m` and
  `conversion_timeout=5s`. In 0.9.2 the chart omits both keys, so the
  module's frozen defaults apply (`conversion_memory=64m`,
  `conversion_timeout=30s`). Upgrading chart users see up to a 6.4x
  looser conversion memory bound and a 6x longer conversion timeout
  unless they set `markdown.limits.conversionMemory` or
  `markdown.limits.conversionTimeout` explicitly. The
  `validate_helm_frozen_defaults` release gate locks the single-source
  contract. The chart must not restate module defaults.

## Retained 25-Directive Contract

The frozen 25-directive surface is the same contract documented in
[MIGRATION-0.9.2.md](MIGRATION-0.9.2.md#final-25-directive-contract)
(that table is the single source of truth to avoid row-level drift between
the two guides). Every directive listed there remains valid in 0.9.2.
The section on [Breaking Semantic Changes](#breaking-semantic-changes) above
covers everything removed.

## Migration Path

1. Read [MIGRATION-0.9.2.md](MIGRATION-0.9.2.md) for before/after examples of
   every removed directive.
2. Update `nginx.conf` to remove/replace removed directives.
3. Replace the module binary with the 0.9.2 build.
4. Run `sudo nginx -t`. Every removed directive now fails with
   `unknown directive`, so the test confirms the migration is complete.
5. Validate the metrics and diagnostics endpoints per the migration guide.
